# Two-Path Convergence: wso2cloud + local-unification PR Saga Synthesis

## 1. Executive summary — the two-path story

The platform must run from ONE codebase across two deployment targets:

- **Local** (`deployments/`): k3d + docker-compose. A *dedicated* OpenChoreo whose Thunder is the only trusted issuer; single org on the default OU; OpenBao for secrets; an in-repo `local-cluster-gateway-proxy` stub and an in-repo `local-secret-manager-api` stub. Namespace already isolates the org, so the BFF talks OC REST direct and reads the namespace from the URL path. Simpler auth (often no Authorization header at all).
- **wso2cloud** (managed, GitOps-deployed, private repo): a *shared* `platform-api` in front of OpenChoreo that **routes and bills by the JWT `ouId` claim**; per-org Thunder OUs + per-org publisher OAuth client-credentials; the real `secret-manager-api` (SM-API) behind ESO; the real `cluster-gateway-proxy` (JWT-validating since #23); ECR pull secrets carried by per-org **namespaced** ComponentTypes; M2M service identity whose own `ouId` is the **Admin OU** (`a5000000-…`).

The recurring failure mode: a single BFF code path that is correct locally silently mis-behaves in cloud because cloud inserts a routing/billing/auth intermediary (platform-api `ouId` routing, gateway jwtAuth, ESO AppRole policies, CP/WP plane split). "Took several PRs" because the team kept trying *coarse* unifications (M2M-only; user-JWT-first; one ctx key for two identities) that broke a third case, then refined.

**The winning meta-pattern (canonized by PR #38 / the 6 ADRs):** *One unified BFF code path; push every local/cloud difference behind a single injected value, a nullable provider/resolver, or an in-repo stub of the cloud service — never an `if cloud … else local …` Go branch. Derive identity/topology (namespace, vault path, OU, token URL) from request scope (JWT `ouId`, URL `namespaces/{ns}`, org handle) rather than from config.*

## 2. The 6 ADRs (distilled endpoints, `docs/adr/000*.md` from PR #38, still UNMERGED so `docs/adr/` is absent from main)

- **ADR-0001 — Coding-agent off the workflow plane.** Coding-agent WorkflowRuns move to the data plane (`cloud-dp-oc-dp`) in namespace `wc-<org8>-<hash8>-remote-worker`; `dockerfile-builder` BUILDs stay on the workflow plane (`workflows-wc-<…>`) with Argo. BFF distinguishes the two at dispatch time. (Saga: workflow-runs-cloud, #10.)
- **ADR-0002 — Local SM-API is an in-repo stub; ONE SM-API provider both envs.** Never an `openbao` provider variant. Local = `deployments/local-secret-manager-api/` Go stub reproducing `POST/GET/DELETE /secrets`, writing OpenBao KV-v2 + creating the OC `SecretReference` CR; namespace derived from JWT `ouId` as `wc-<first8>-<sha256[:8]>` (identical to BFF `OrgBaseNamespace` and cloud SM-API). Mirrors the `local-cluster-gateway-proxy` stub precedent. Rejected: two-binary open-core split, running the private cloud binary, prebuilt image. (Saga: sm-api, #37; arc #10→#27→#37.)
- **ADR-0003 — Coding-agent dispatched as a plain K8s Job via cluster-gateway-proxy**, not an OC WorkflowRun (no Argo on DP). Dispatch = Namespace→SA→ExternalSecret×N→Job posted through the proxy. Cloud proxy now validates platform-idp JWTs (#23) so BFF attaches its M2M token; local stub is unauthenticated (nil auth provider). (Saga: workflow-runs-cloud + cluster-gateway-proxy-auth, #10, #23.)
- **ADR-0004 — Reference per-org namespaced `kind: ComponentType` unconditionally** (carries `imagePullSecrets` for per-org ECR); local `setup-asdlc.sh` provisions the namespaced `service`/`web-application` types in the org ns `default`, derived verbatim from the cluster-scoped specs, as the local stand-in for cloud `ProvisionOrgUnit`. Rejected: env-conditional kind in Go. (Saga: componenttype, #36 + commit 8ebfaec, #37.)
- **ADR-0005 — Dual-mode OC auth + impersonation.** User-initiated calls FORWARD the inbound user JWT (platform-api routes/bills by its `ouId`). Async/service calls carry the BFF M2M token AND set `X-Impersonate-Org` to the target org UUID resolved from the URL `namespaces/{ns}` segment, keyed by org **handle**, preferring Thunder `ouId`. A distinct ctx marker `middleware.WithServiceIdentity`/`IsServiceIdentity` (NOT "is user JWT absent") signals service vs user; an M2M token never sits in the user-token ctx key; resolver miss **aborts** the call (never silently mis-bills to Admin OU). Local seam: `ImpersonateOrgResolver == nil`. (Saga: oc-auth-routing, arc #15→#16→#17→#18→#19→#20→#21→#22.)
- **ADR-0006 — Build git credentials via OpenChoreo `CreateGitSecret`** (OpenBao + per-org `SecretReference app-factory-component-build-git-secret`), refreshed (delete+create, OC has no update verb) every build because the App token is short-lived. SAME path local+cloud; rejected a `BUILD_GIT_SECRET_VIA_OC` two-path flag. INTERIM: cloud `/gitsecrets` unrouted (blocked on wso2cloud#319) → cloud creates **public** repos + clones unauthenticated and degrades to empty `secretRef`; local keeps **private**. (Saga: build-git-secret, #33, #34.)

## 3. Per-saga narrative (chronological, with dead-ends)

### Saga: infra/org-migration (#1, MERGED)
Seed import from private `wso2-enterprise` org into public `wso2/labs-agentic-engineer`; squashed ~100 commits, re-homed module roots to `github.com/wso2/asdlc`. Landed every dual-path seam at once (incl. kaje94's #16/#17/#25/#30/#31/#32/#33/#35 work). Already designed the central convergence mechanism: optional `openchoreo.Config.ImpersonateOrgResolver` (nil → direct-OC local) instead of an env branch; the `config.go` seam comments are effectively the refactor spec. **Final state:** foundational, not superseded.

### Saga: workflow-runs-cloud (#10, MERGED) — ADR-0001/0003
The old dispatch was wholly broken in cloud: `git-service` cross-cluster SSA'd plaintext Secrets into `workflows-<org>` on the WP cluster, which silently no-op'd (no cross-cluster K8s reach) → agent never got its Anthropic key/PAT. #10 moved coding-agent off Argo/WP onto a plain K8s Job on DP via `cluster-gateway-proxy`, replaced the SSA push with SM-API SecretReference + per-run ExternalSecrets (ESO), folded `git-service` into `asdlc-service` (one binary), and moved CP git to the GitHub Git Data API. Introduced two identical HTTP contracts with env-swapped backends: real cloud proxy vs `local-cluster-gateway-proxy` (~300 LOC reverse-proxy stub to k3d); the REAL cloud SM-API binary run locally (later replaced by an in-repo stub in #37). Namespace DERIVED from `orgUUID` via sha256, not config. Self-flagged follow-ups WS2.4 (per-org Thunder cc) and WS2.6 (cut legacy ClusterWorkflow). **Final state on main:** codingagent pkg, clustergatewayproxy + secretmanagersvc clients, local stub all survive; `git-service` gone; `tryDispatchViaProxy` vs legacy ClusterWorkflow fallback still present (WS2.6 not landed).

### Saga: gitservice-collapse (#13, MERGED)
WS0.1 had folded git-service into the binary but kept a loopback HTTP client to `http://localhost:9090`. In cloud `GIT_SERVICE_BASE_URL` resolved to the standalone git-service Service which wso2cloud-deployment#2222 had scaled to 0 → every credential/issue/artifact path 503'd; local worked by accident (loopback hit same binary). #13 deleted the 1,824-LOC loopback client, rewired ~16 consumers to in-process services, added `controllers/credential_errors.go` to preserve HTTP error shapes, collapsed `GIT_SERVICE_BASE_URL`+`AGENT_GIT_SERVICE_URL` into one `AGENT_PLATFORM_URL`, and deleted the per-target git-service Service-JWT client (no boundary to auth). **Final state:** kept; one runner reach-back URL whose *value* (not branch) differs per env.

### Saga: managed-db (#11, MERGED)
Cloud managed-RDS provisioning REVOKE'd privileges to DML-only, stripping REFERENCES/TRIGGER ACL bits, so a raw-SQL FK migration (`phase3_coding_agent_logs`) crashed the pod. Fix: `RunBootstrapGrants` runs owner self-grant (`GRANT ALL … TO CURRENT_USER` + `ALTER DEFAULT PRIVILEGES`) before any migration — no-op locally, self-heal in cloud. Env-agnostic, idempotent, keyed on `CURRENT_USER` (derived from the live connection, not config). **Final state:** kept; CodeRabbit caveat — must run before AutoMigrate.

### Saga: oc-auth-routing (#15→#16→#17→#18→#19→#20→#21→#22) — ADR-0005. The longest, most instructive arc.
Cloud-only bug: platform-api routes/bills by token `ouId`; the seeded M2M client's `ouId` is the Admin OU, so every async OC write hit `wc-a5000000` and 402'd on empty entitlement; `GET /organizations` returned the admin's (empty) list.
- **#15** (worked-then-superseded): flipped `authToken` to user-JWT-first, M2M fallback. Aligned with the already-working agent-manager pattern but a 2-valued precedence can't model "async write inside a user request that must act AS the org."
- **#16** (diagnostic-temporary): instrumented minted-JWT claims + a logging RoundTripper with `auth_source` tag; confirmed `ouId=Admin`. Reverted by #17.
- **#17** ("Plan A" phase 1, worked-then-superseded): reverted #16 and went **M2M-only** (BFF talks OC REST direct, bypass platform-api). CORE DECISION REVERSED — M2M-only made list-orgs filter by the M2M client's own `ouId` (wrong/empty) and mis-routed user writes. Only #17's error-propagation (`authToken` → `(string,error)`, abort on mint failure) survived.
- **#18** (worked-then-superseded): restored user-JWT forwarding AND added `X-Impersonate-Org` via a new `Config.ImpersonateOrgResolver` + `namespaceFromPath`. But it gated M2M on `GetAuthToken(ctx)==""` — wrong, because orchestration runs inside a user request (a JWT IS in ctx), so impersonation never fired.
- **#19** (merged into #18's branch): the impersonation half (`X-Impersonate-Org` on M2M, resolver prefers Thunder `ouId`).
- **#20** (chore): observability for CGW dispatch + impersonation header decision.
- **#21** (worked-and-kept): THE fix — replaced the `tokenInject` closure (which stuffed M2M into the user-JWT ctx key) with an explicit `middleware.WithServiceIdentity`/`IsServiceIdentity` marker; transport branches on `IsServiceIdentity(ctx) || userJWT=="" || ImpersonateOrgResolver==nil`. Regression test: ctx with BOTH user JWT and marker must impersonate. **"Never overload one context key for two identity meanings."**
- **#22** (worked-and-kept, wso2cloud-only): fixed a 3-way org-identity key mismatch — BFF uses org **handle** as the OC namespace; platform-api returns canonical `wc-<uuid8>-<hash8>` in `metadata.name`; Thunder embeds `ouId` in the JWT. `orgUUIDResolver` now returns `claims.OuId` when the JWT handle == namespace (DB-free), and `backfillRow` is keyed by handle, not the canonical name.
**Final state on main:** dual-mode transport with the `WithServiceIdentity` marker + handle-keyed resolver; local stays no-header via `ImpersonateOrgResolver==nil`.

### Saga: cluster-gateway-proxy-auth (#23, MERGED)
Once the entitlement chain was fixed (CreateComponent 201), dispatch hit 401 from the cloud proxy (now JWT-validating). #23 added an optional structural `AuthProvider` to the CGW client, REUSING the same `oauth.TokenProvider` the OC client already carries (no new credential). Non-nil in cloud (Bearer M2M), nil local (no header). **Final state:** kept; "make outbound platform-plane auth one injected provider per client."

### Saga: coding-agent-secrets (#24, CLOSED)
Comment-only correction: per-org coding-agent ExternalSecrets must use `secretstore-read` (AppRole grants `user-app-secrets/*`), NOT `application-secrets-read` (403s). The actual store is `AGENT_CLUSTER_SECRET_STORE` at deploy. CLOSED — superseded by #38's dispatcher.go comment fix (which itself never reached main, so main still carries the inverted comment). Lesson: validate the store against the AppRole policy at startup; consolidate the doc to one place (it was duplicated across dispatcher.go/config.go/externalsecret_template.go).

### Saga: publisher-cc (#12 CLOSED → #26 MERGED; then #28, #29, #30) — runner→BFF auth
Replace the bespoke BFF-minted RS256 TaskJWT (`ASDLC_BEARER`) with per-org Thunder client-credentials (the agent-manager pattern), so the runner can pass the cloud gateway's jwtAuth.
- **#12** (CLOSED): first attempt against pre-in-process-refactor main; closed to avoid duplicate review surface.
- **#26** (MERGED): ported onto post-refactor main. `PublisherTokenVerifier` (JWKS RS256, audience `asdlc-publisher-<orgHandle>`, `ouHandle==orgHandle` cross-org defense); `authorizeRunnerCallback` dual-mode verify (TaskJWT then cc); `SMAPIWriter.WritePublisher` mirrors the cc secret + stamps a 4-col SM-API triplet on `organization_idp_profiles` (phase8 migration); dispatcher emits a 2-entry ExternalSecret; `deriveTokenURLFromJWKS`. Additive, gated on data presence (triplet present) + capability (`thunderJWKS != nil`), not an env flag; legacy bearer kept (WS2.6 to remove).
- **#28** (MERGED): publisher was only provisioned by `trait_sync` on the first API-SECURED deploy, but the runner runs for EVERY component → non-protected components got no publisher and the gateway 401'd. #28 calls `idp.EnsureOrgPublisher` at dispatch for every component, and uses a URL-scheme heuristic `isGatewayPlatformURL` (https → cloud, publisher cc mandatory and fail loud; http → local, per-task bearer fallback).
- **#29** (MERGED): multi-org cloud bug — `EnsurePublisherApp` registered the app under the DEFAULT OU, so every org's cc token carried the default OU's `ouHandle` and the verifier rejected it. Fix: register under the org's own Thunder OU (`Organization.ThunderOrgUUID = JWT ouId`), delete+recreate self-heal for wrong-OU apps, self-heal stale cached issuer/jwksURL. Single-org local masked it (default OU == the one org's OU).
- **#30** (MERGED, wso2cloud-only): harden the self-heal — Thunder returned 500-but-actually-deleted on DELETE; re-check by name and continue to recreate. Local never hits it (single-org, wrong-OU branch never fires).
**Final state on main:** dual-mode runner auth (TaskJWT + publisher cc) coexists; cc gated on triplet/JWKS presence; publisher registered under org OU.

### Saga: local-secrets (#27, CLOSED) → folded into sm-api (#37, MERGED)
After a k3d teardown wipes OpenBao, SM-API metadata triplets on cred rows point at vanished vault paths → ExternalSecrets unsyncable, runner pods hang. #27 added a local-only `POST /_test/sm-api-resync` (TestMode AND `LocalOpenBaoRepairEnabled` — a SECOND flag because `TEST_MODE=true` is already set on the cloud dev binding for `_test/reset`) + `repair-secrets.sh` (kubectl-context-gated) doing shell→vault `kv put`. CLOSED — commits folded into #37. Lesson: a single flag must map 1:1 to a capability; don't multiplex.

### Saga: webhook (#31 MERGED; #35 MERGED)
- **#31**: cloud gateway forwards GitHub deliveries verbatim as `/api/v1/webhooks/github` (jwtAuth off), but BFF only registered `/webhooks/github` → fell into the JWT-gated `/api/` subtree and 401'd. Fix: mount the same HMAC handler at BOTH paths; divergence confined to the outbound `GITHUB_WEBHOOK_DELIVERY_URL`.
- **#35** (wso2cloud-only): multi-tenant correctness — webhook task lookups scoped by `project_id` alone, but `project_id` is a per-org slug reused across orgs (`test-dev-5` in 3 orgs). `lookupProjectByRepo` now returns `(orgID, projectID)` from the globally-unique `git_repositories` row; all 4 resolvers scope by `(org_id, project_id)`. Single-org local was the N=1 case.

### Saga: build-git-secret (#33 MERGED; #34 MERGED) — ADR-0006
- **#33** (worked-then-superseded by #34's fold): provision build git secret via OC `CreateGitSecret`, unified local+cloud (rejected a per-env flag).
- **#34**: tasks stuck at `merged`, never `building` — cloud platform-api doesn't route `/api/v1alpha1/gitsecrets` (404, blocked on wso2cloud#319). Fix: degrade `StageBuildSecret` to empty `secretRef` on provisioning failure (clone unauthenticated, OK for public repos); flip `GITHUB_REPO_VISIBILITY` default private→public (cloud inherits public, local overlays keep private); tolerate OC 409 on concurrent same-org GitSecret create. Behavioral fork pushed entirely into deployment config; the degrade branch becomes dead code once #319 lands.

### Saga: componenttype (#36 MERGED + commit 8ebfaec) — ADR-0004
Cloud workloads stuck ImagePullBackOff — `kind: ClusterComponentType` resolves to OC's built-in with no `imagePullSecrets`. Fix: reference `kind: ComponentType` (per-org namespaced) unconditionally; follow-up provisions the namespaced types locally in `setup-asdlc.sh` (derived from the cluster-scoped specs) so the same kind+name resolves in both envs. Divergence pushed to infra provisioning (cloud `ProvisionOrgUnit` / local setup), not Go code.

### Saga: sm-api (#37, MERGED) — ADR-0002
Removed the only `../../wso2cloud` build dep (which blocked public users from `docker compose up`) by adding `deployments/local-secret-manager-api/` — a byte-parity stub (vault KV-v2 layout, SecretReference CR, `ouId`-derived namespace, managed-by label, error JSON). Bundled the #27 repair surface (re-fenced behind `LOCAL_OPENBAO_REPAIR`, set false in the cloud helm chart), the #36 local ComponentType provisioning, and a JobWatcher `ca-%` run-name filter so proxy and legacy watchers coexist. **Final state:** the asdlc-service sm-api client sees an identical contract both paths; divergence contained inside one replaceable binary.

Doc-only: commits `docs/adr/0001-0006` + refreshes CONTEXT.md to match shipped code; rides a dispatcher.go `ClusterSecretStoreName` comment correction (which did NOT reach main). **Final state:** decisions SHIPPED via other merged PRs, but `docs/adr/` is absent from main and main still carries the inverted ClusterSecretStore comment.

## 5. Unifying principles (what made the two paths converge)

_Each is the canon the refactor should make structural rather than incidental._

1. One unified BFF code path; every local/cloud difference is a single injected value, a nullable provider/resolver, or an in-repo stub of the cloud service — never an `if cloud … else local …` Go branch. This is the explicit canon of PR #38 and applies across SM-API (ADR-0002), ComponentType (ADR-0004), build-git-secret (ADR-0006, which rejected a BUILD_GIT_SECRET_VIA_OC flag), and OC auth (ADR-0005). Proof PRs: #1, #10, #36, #37, #38.

2. Derive identity/topology from request scope, never from config: namespace = wc-<first8>-<sha256[:8]> from JWT ouId (#10, #37/ADR-0002); impersonation org = URL namespaces/{ns} segment keyed by handle, preferring Thunder ouId (#18/#19/#22/ADR-0005); publisher OU = org's own Thunder OU (#29); publisher token URL = derived from the org JWKS URL (#26 deriveTokenURLFromJWKS); managed-DB grant identity = CURRENT_USER from the live connection (#11). Config toggles are the seam of last resort.

3. Auth intent must be an explicit first-class signal, not inferred from incidental context state: the user-vs-service-identity decision is a positive middleware.WithServiceIdentity marker (own ctx key), and an M2M token is never stored under the user-JWT ctx key. The #15→#18 attempts that inferred it from `userJWT==''` all mis-fired because orchestration runs inside a user HTTP request; #21 (worked-and-kept) + ADR-0005 are the resolution.

4. One M2M oauth.TokenProvider serves every outbound platform-plane client (OpenChoreo, cluster-gateway-proxy, SM-API), attached as Bearer only when present; its presence/absence (driven by SERVICE_AUTH_* env) is the single local-vs-cloud auth fact. Local k3d runs its proxies with auth middleware disabled so the SAME code sends no header. Proof: #23 (reused the OC token for CGW, no new credential), #1, ADR-0003 status update.

5. Define each cloud-only capability as ONE narrow HTTP contract and supply a different implementation per environment — run the real cloud binary where possible, write a tiny same-shape in-repo stub where not — so the BFF has zero `if cloud` branches and local testing exercises the cloud code path. Proof: cluster-gateway-proxy (real proxy vs local-cluster-gateway-proxy ~300 LOC, #10) and secret-manager-api (real SM-API vs deployments/local-secret-manager-api byte-parity stub, #37/ADR-0002).

6. Tenant identity flows through the whole pipeline as a first-class key derived from a globally-unique anchor (the git_repositories row / repo URL), never from a per-org slug (project_id, unique only within an org). Single-org local is the N=1 case of the same correctly-scoped code, so there is no separate path to maintain. Proof: #35 (webhook (org_id, project_id) scoping); reinforced by the plan's whole §5.1 tenancy thesis.

7. Idempotent, env-agnostic operations absorb the divergence at runtime instead of branching: a safe no-op in the permissive env and a self-heal in the restrictive one. Proof: #11 (owner self-grant heals managed-DB REVOKE, no-op locally), #34 (degrade to empty secretRef when the cloud /gitsecrets capability is absent), #36 (provision the same-named namespaced ComponentType in both envs), #29/#30 (idempotent EnsureOrgPublisher self-heal under the org OU).

8. Each flag maps 1:1 to a capability, gated by environment identity, not by reusing a convenience switch: a SECOND distinct flag (LOCAL_OPENBAO_REPAIR) had to be invented because TEST_MODE was already true on the cloud dev binding and would have exposed decrypted per-org plaintext. The cloud helm chart sets LOCAL_OPENBAO_REPAIR=false to opt out by default. Proof: #27 (closed), #37/ADR-0002.


## 6. Open divergences still living in `main` (the seams the refactor must absorb)

## 7. Learnings → proposed edits to `asdlc-service-modularization.md`
_The actionable output: how to fold each learning into the restructure so "works in both paths" becomes a property of the architecture (which feature/platform package OWNS each divergence, in which phase)._

### 7.1  OC auth is governed by three implicit conditions scattered in the transport editor — ImpersonateOrgResolver (nil-vs-set), IsServiceIdentity(ctx), GetAuthToken(ctx) — and it took 8 PRs (#15→#22) to settle. The plan already hoists this into platform/auth + the OC adapter and fixes IDOR-6, but it does NOT make the user-vs-service-identity CALL MODE a first-class typed value chosen once at the edge; it leaves the per-request branch `useServiceIdentity := IsServiceIdentity(ctx) || userJWT=='' || ImpersonateOrgResolver==nil` intact.

**Plan section:** §5.1 (IDOR-6 impersonation fix) + §4.0 platform/auth + §5.2 OC adapter (clients/openchoreo/occlient)

**Proposed edit:** In §5.2, make the OC adapter expose ONE method that takes an explicit identity intent (e.g. `ForCaller(ctx)` reading `Caller.Source`): SourceUserJWT → forward user JWT, all service sources → M2M + X-Impersonate-Org from `Caller.ThunderUUID` (already on the Caller per §5.1a, no namespaceFromPath re-parse). Add an ADR-0005 callout: the local seam is the absence of the impersonating adapter impl (DirectOC adapter), selected once at the composition root by deployment scope — NOT a per-request `ImpersonateOrgResolver==nil` check. This deletes the `userJWT==''` heuristic that #18 got wrong and #21 had to patch.

### 7.2  #1, #10, #23 converge OC, CGW, and SM-API auth onto the SAME one M2M oauth.TokenProvider whose mere presence/absence (driven by SERVICE_AUTH_* env) encodes local-vs-cloud. Each new platform client (#23) re-discovered the 401 because the shared provider wasn't baked into the client constructor contract. The plan §5.2 reconciles token providers onto token.Source but treats it as interface-tidying, not as the single local/cloud auth seam.

**Plan section:** §5.2 (token providers reconcile onto token.Source/Invalidator) + §4.0 platform/httpx

**Proposed edit:** State explicitly that token.Source is THE single 'outbound platform-plane auth' seam: one provider injected into every platform client (OC, CGW, SM-API), nil in local (k3d proxies run auth-off) and the M2M provider in cloud. Add to §5.2: every clients/ adapter constructor takes an optional token.Source and attaches Bearer when non-nil; ban a client minting its own credential. This is what makes #23's 'reuse one credential' a structural property and prevents the next client re-hitting 401.

### 7.3  The wc-<first8>-<sha256[:8]> namespace derivation from JWT ouId is independently re-implemented in THREE places (cloud SM-API auth.GenerateNamespaceName, BFF OrgBaseNamespace, local stub generateNamespaceName per ADR-0002) plus RemoteWorkerNamespace. If any drifts, BFF/SM-API/ESO disagree on the vault path silently.

**Plan section:** §4.0 platform/tenant (owns WorkflowPlaneNamespace/RemoteWorkerNamespace) + §5.1

**Proposed edit:** Make platform/tenant the SINGLE authoritative home for ALL namespace derivations: add OrgBaseNamespace(ThunderUUID)→wc-<first8>-<sha256[:8]> next to RemoteWorkerNamespace/WorkflowPlaneNamespace, all keyed off Caller.ThunderUUID (scope, never config). Note that the in-repo local-secret-manager-api stub must import this same derivation (or a copied-with-citation mirror, tested for byte-parity) — add a contract/parity test to §7 asserting stub.namespace == tenant.OrgBaseNamespace for a sample ouId.

### 7.4  The local↔cloud convergence pattern is 'in-repo stub of each cloud-only service behind ONE HTTP contract' (local-cluster-gateway-proxy #10, local-secret-manager-api #37), so local testing exercises the cloud code path. The plan moves clustergatewayproxy and secretmanagersvc into adapters but never names the stubs as first-class, owned, parity-tested artifacts of those features.

**Plan section:** §4.2 credentials (adapters/{smapi}) + §4.10 codingagent (adapters/clustergatewayproxy)

**Proposed edit:** Add to §4.2 and §4.10 that each cloud-only-service adapter OWNS its in-repo local stub as a sibling (e.g. credentials/adapters/smapi ships the contract test that BOTH the real client and deployments/local-secret-manager-api must satisfy; codingagent/adapters/clustergatewayproxy similarly for local-cluster-gateway-proxy). Promote 'in-repo stub behind one HTTP contract' to a named §5 sub-pattern so future cloud-only services follow it instead of an openbao-style structurally-different local provider (ADR-0002 rejected alternative).

### 7.5  Publisher-cc provisioning (#28/#29/#30) and trait_sync both ensure the per-org Thunder publisher; #28 had to add EnsureOrgPublisher to dispatch because trait_sync only ran it on the first API-secured deploy. The plan splits IDPService (idp) from dispatch (codingagent) and trait_sync (component) but doesn't designate a single owner of 'ensure per-org publisher exists'.

**Plan section:** §4.3 idp (IDPService) + §4.10 codingagent (Dispatcher) + §4.8 component (TraitSync)

**Proposed edit:** In §4.3 make idp publish a single EnsureOrgPublisher port (idempotent get-or-create + SM-API mirror + org-OU registration with the #29 self-heal and #30 5xx-on-delete tolerance) that BOTH codingagent dispatch and component trait_sync consume via a narrow consumer port. Add to §4.10: dispatch calls idp.EnsureOrgPublisher for every component before reading PublisherSR; the cloud 'publisher mandatory vs local bearer-fallback' fork becomes a typed RunnerAuthMode on the deployment env (NOT #28's isGatewayPlatformURL https-string sniff).

### 7.6  The cloud-vs-local fork for runner auth (#28) is a leaky heuristic: isGatewayPlatformURL sniffs https:// on AGENT_PLATFORM_URL to mean 'gateway-fronted, publisher cc mandatory'. The real distinction is whether an auth gateway sits in front of the BFF. Same shape recurs in remote-worker (#25): node:https vs node:http branched per-call in workspace.ts AND skills_pull.ts.

**Plan section:** NEW (runner-auth seam not explicitly modeled) + §4.10 codingagent

**Proposed edit:** Add a NEW §5.6 'Runner identity & transport': (a) replace the https-URL heuristic with an explicit RunnerAuthMode/gatewayFronted bool on a DeploymentEnv provider injected at the composition root; (b) note that the remote-worker (TS) must route every worker→platform call through ONE http client helper that branches on url.protocol once (centralizing the #25 fix), so cloud's https gateway URL never re-surfaces as 'Protocol https: not supported' in a new caller; (c) derive the publisher token URL from the org JWKS URL (deriveTokenURLFromJWKS), not a separate config var.

### 7.7  Flags must map 1:1 to capabilities. #27/#37 had to invent LOCAL_OPENBAO_REPAIR because TEST_MODE was already true on the cloud dev binding (for _test/reset), so reusing it would have exposed decrypted per-org plaintext in cloud. The plan flags INT-4/INT-5 but frames the multi-flag gate as acceptable rather than as a 1:1 capability principle.

**Plan section:** §3 INT-4/INT-5 + §8 Phase 8 (_test/reset org-scope, dev-only flag) + §5.5 composition root

**Proposed edit:** Add to §5.5 a 'one flag = one capability, gated by env identity not by reusing convenience switches' rule, and to §8 Phase 8: collect all dangerous-local-only surfaces (sm-api-resync, _test/reset) behind distinct flags that the cloud release binding/helm chart sets false by default (cite ADR-0002/#37's LOCAL_OPENBAO_REPAIR=false in the helm chart as the proven opt-out). The SecretProvider local impl should self-reseed on startup (a provider method) so no out-of-band repair-secrets.sh + plaintext-emitting endpoint is needed at all.

### 7.8  Loopback HTTP clients are latent dual-path bugs: #13 showed GIT_SERVICE_BASE_URL meant 'same binary' locally but 'dead scaled-to-0 Service' in cloud. When two services merge into one binary, collapse to in-process interfaces immediately and keep exactly one runner reach-back URL whose value (not presence/branch) differs.

**Plan section:** §4.4 gitrepo (absorbed git-service) + §5.5 composition root

**Proposed edit:** Add an explicit note to §4.4 that the absorbed git-service is consumed ONLY via in-process feature ports (RepoService/CredentialService/etc.), never a loopback HTTP client, and that the cross-service Service-JWT auth is deleted (no boundary). In §5.5, state that runner reach-back collapses to one AGENT_PLATFORM_URL whose value differs per env — forbid parallel AGENT_GIT_SERVICE_URL-style vars (a depguard/grep check).

### 7.9  Env-agnostic idempotent operations beat env branches: #11 (CURRENT_USER self-grant), #34 (degrade-to-empty-secretRef on missing capability + config-driven visibility), #36 (provision same-named resource in both envs). The plan's bootstrap package owns migrations but doesn't capture the 'safe no-op locally, self-heal in cloud' bootstrap idiom or the 'degrade on absent capability' idiom.

**Plan section:** §4.0 platform/bootstrap (DB open + 16-phase migration runner) + §4.5 artifacts/§4.2 credentials (build secret)

**Proposed edit:** Add to §4.0 bootstrap that the migration runner runs RunBootstrapGrants (owner self-grant keyed on CURRENT_USER) before AutoMigrate as a permanent env-agnostic step (per #11 CodeRabbit ordering caveat). Add to §4.2 (BuildCredentialsService) that build-credential provisioning is modeled as one provider whose failure degrades gracefully (empty secretRef → unauthenticated clone for public repos), with repo visibility entirely in deployment config (GITHUB_REPO_VISIBILITY); note the degrade branch becomes dead code once wso2cloud#319 lands and both planes converge on a real secretRef.

### 7.10  Tenant identity must flow as a first-class key derived from a globally-unique anchor, not a per-org slug — #35 fixed webhook task resolution by scoping (org_id, project_id) from the globally-unique git_repositories row; single-org local was just the N=1 case. This is exactly the plan's core tenancy thesis, and #35 is concrete proof it collapses the local/cloud distinction.

**Plan section:** §4.11 webhook (INT-2) + §3 INT-2 + §4.4 gitrepo (composite (org_id,project_id) unique)

**Proposed edit:** Cite #35 explicitly in §4.11/INT-2 as the shipped precedent: resolve (orgID, projectID) once at the webhook boundary from the globally-unique repo row and thread it through Router.Dispatch; the unanchored repo_url ILIKE LIMIT 1 is the exact bug #35's predecessor had. Reinforce in §9 Risk 3 that single-org local masks cross-org slug-collision bugs, so the two-org-same-slug test kit (§7) is the forcing function — #35 is the merged evidence the composite (org_id,project_id) index in §4.4 F2 is required.
