# Git-Operations Inventory — aep-api & agents-service

> **Scope.** Every git/GitHub operation performed by `services/aep-api` and
> `services/agents` (the agents-service), framed as **scenario → operation**.
> The isolated remote coding-agent worker is *out of scope* except where it
> establishes a convention the shared-volume refactor should converge with
> (called out explicitly in §8).
>
> **Companion.** The refactor these operations feed into is designed in
> [`shared-volume-clone-architecture.md`](./shared-volume-clone-architecture.md).
>
> **Generated** from a 7-reader + completeness-critic sweep. Mechanism legend:
> `API·git-data` = GitHub Git-Data API (blobs/trees/commits/refs/tags),
> `API·rest` = GitHub REST (repos/issues/webhooks/apps), `inline` = codebase
> shipped in the agent-turn payload, `fs` = local filesystem, `db` = Postgres only.

## 9. Cross-cutting observations

The load-bearing facts for the redesign — read these before the design doc.

**C1.** Round-trips per codebase read TODAY: one full read = GetRef + GetCommit + GetTree(recursive) + N×GetBlob (one HTTP call PER FILE). This N+3 fan-out is re-implemented independently in FOUR features (artifacts/git_reader.go, files/files_service.go, skills/repo_store.go, genai/genai_reads.go) each with its own HEAD-SHA/soft-TTL cache. The shared mount collapses all four to one `git pull` + a filesystem walk — the single largest efficiency win and the strongest argument for one unified clone abstraction replacing four bespoke walkers.

**C2.** There are already THREE local-working-tree clone actors in the repo the refactor should learn from / converge with, none owned by aep-api: (1) the coding-agent runner (workspace.ts real git clone+push+PR), (2) the OpenChoreo build checkout-source (clones repo_url@commit), and (3) the gittest harness (services/aep-api/internal/platform/gittest — real bare repo + working clone + a faithful Git Data API fake). gittest is literally the proving ground for the mount model and its Git-Data fake would be superseded by real local commits.

**C3.** Multi-tenant directory layout is already de-facto standardized as <orgId>/<projectId>/<taskId> by the runner (workspace.ts computeLayout). The mount should adopt <org>/<project>/<repo> (dropping the per-task leaf, adding multi-repo/component support) plus a distinct per-org org-skills clone. The tenancy key everywhere is (org_id, project_id)→repo_url via git_repositories (composite-unique), and repo_url is normalized in two forms — the path deriver must match that normalization.

**C4.** Concurrency across replicas is currently handled entirely by GitHub-side optimistic concurrency: UpdateRef(force=false) fast-forward CAS (casAttempts=4) for commits, and CreateTagRef 422 for tag collisions — there is NO local lock. On the mount this splits into TWO problems: (a) intra-node working-tree contention (multiple turns/tasks on one clone) which git's index lock does NOT safely arbitrate across processes, and (b) inter-node push races which remain and become push-rejection-after-pull-rebase retries. The mount ADDS a divergence/merge dimension the pure-CAS model never had.

**C5.** Conflict-retry semantics must be re-expressed twice: file-apply CAS (baseSha precondition → 409) becomes 'compare baseSha against the local committed/index blob then push --force-with-lease, retry on non-FF after pull --rebase'; tag-collision retry becomes fetch-tags + recompute + re-push. The sha:null-deletion + base-tree-overlay tree assembly (in artifacts + skills commit paths) all collapses into native git index add/rm — a large simplification, but the retry LOOPS (conflict_retry.go leaky bucket keyed org:project) must be preserved as push-rejection handlers.

**C6.** Skills and codebase are the SAME shape problem: both are read via the identical GetRef/GetCommit/GetTree/GetBlob walk and both are shipped inline (Files map + Skills[]). Both the agents-service (inline) AND the coding-agent runner (HTTP pull + fs materialize) already prove the two consumers want files on disk. Preserving the per-org org-skills repo as a first-class second mount (alongside project repos) is mandatory; core/flow skills currently go:embed'd into aep-api must also be seeded onto the mount or bundled so agents read ALL skills from one place.

**C7.** Issues/labels/PRs/webhooks/installations have NO local-clone equivalent and STAY GitHub REST after the refactor (Tasks are issues; execution funnel is label-driven; PR state is GitHub-native). The mount touches ONLY git-object reads/writes on specs/ and component code. This is the hard boundary: the GitHub client cannot be replaced by a clone — roughly the entire IssueOps/WebhookOps/AppInstallOps surface plus CompareRefs' /compare endpoint (the one diff primitive not expressible as a local walk today, which DOES become `git diff` on the mount) remain remote.

**C8.** Repo/commit/tag coordinates are persisted in FOUR places that must stay consistent with the mount's clone-path map: git_repositories (repo_url, default_branch, repo_slug, webhook_id), executions (repo owner/name, commit_sha=merge SHA, design_tag), the OpenChoreo Component CR (Repository.url/branch/appPath), and the Task issue-body machine block (specTag/designTag lineage). The merge commit_sha on the executions row is exactly what a mount build must `git checkout`; the lineage tags in issue bodies must be fetched into any clone that peels/compares them.

## 10. Open design gaps

Unresolved questions the shared-volume design must answer (each is addressed in
the companion design doc).

**G1.** Two-writers-on-one-working-tree: the coding-agent runner and (post-refactor) aep-api/agents-service would all mutate the SAME shared clone. There is ONE .git/config, ONE index, ONE checked-out branch per clone — concurrent tasks/turns on the same repo would race on branch checkout, index locks, and identity rewrites. The design must decide: one clone per (org,project,repo) with a per-repo lock/queue, OR per-turn/per-task git worktrees off a shared object store, OR keep the runner on its own clone. Nothing in the codebase serializes cross-actor working-tree access today (agents-service TurnGuard only serializes per-conversation-id, not per-repo).

**G2.** Uncommitted-draft materialization: genai turns carry the FE's uncommitted draft inline (filesChangedExternally). To let agents read it off the mount, aep-api must WRITE the FE draft into the working tree (dirty, uncommitted) before dispatch and pin a ref — but that dirties a shared clone other actors read. Needs per-session worktree or a scratch overlay; unresolved.

**G3.** Installation-token expiry vs long-lived clones: App installation tokens expire ~1h; the current per-op credhelper refresh masks this. A server-owned mount clone doing occasional pulls/pushes must refresh the token before each remote op and handle mid-op expiry — no such refresh-before-pull seam exists in aep-api's git path today (it mints per-call for API requests).

**G4.** Pull-failure / divergence handling has no home: every 'becomes git pull' mapping assumes clean fast-forward. Non-FF divergence (another replica or the runner pushed), detached/dirty working trees, and partial-clone corruption need an explicit recovery policy (reset --hard? re-clone? conflict surface?) that the CAS-retry-over-Git-Data model never had to define.

**G5.** OpenChoreo build plane is a separate clone actor in a separate namespace — the design must decide whether the RWX mount spans the OC build plane (so builds read the authoritative clone at the merge SHA) or OC keeps its own checkout-source clone; today there are up to THREE independent clones of the same repo (runner emptyDir, OC build, future aep-api mount) plus the GitHub Git-Data view.

**G6.** RWX StorageClass does not exist in the chart (only postgres RWO PVC); single-node k3d can fake RWX via hostPath, but production needs a real ReadWriteMany class (NFS/EFS/CephFS). agents replicas is hard-coded to 1 and would need to stay 1 or coordinate on the shared volume.

**G7.** Disk lifecycle/GC: no component owns reclaiming clones on project delete, org disconnect, or App uninstall. DeleteRepo only removes the DB row; disconnect only flips status + GC secrets. A new sweep must evict stale/orphaned clone directories and cap disk.

**G8.** Tag lineage across replicas: tag-name collision (v<N>, v<N>-<M>) is caught today by the Git Data API 422 on CreateTagRef. On the mount, `git tag` is local and only fails on push; concurrent replicas can pick the same next tag and both commit locally before either pushes. The recompute-next-tag retry must move to push-rejection handling with a fetch-tags precheck, and lineage tags (specTag/designTag embedded in issue bodies) must be fetched into every clone that needs to peel/compare them.
