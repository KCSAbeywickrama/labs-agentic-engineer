Version `v1`: the spec is `specs/` at tag `v1`.

- [ ] **foundation** Shared setup and product-wide requirements: `events-api`, `events-webapp`, `registration-service`. Scaffold all three components first. Wire Thunder sign-in (P1) with gateway-assertion verification and the scope gates from security.json in the events API and the web app. Support several roles per person (P2). Create the registration-service skeleton, and call it only from the events API (P3).
- [ ] **F1** Events, sessions and rooms: `events-api`, `events-webapp`. Build events, rooms and sessions with the room-overlap and room-capacity checks. Event capacity is stored here but seat counting is F4. Leave F1.7 speaker assignment until F3 gives accepted proposals, and the delete-with-registrations block until F4 exists.
- [ ] **F2** Talk proposals: `events-api`, `events-webapp`. Build the call for proposals, proposal submit, edit and withdraw, and the organizer's filterable list. Edit and withdraw are allowed only while a proposal is submitted and has no scores. F2.4 decision display depends on F3's decide endpoint.
- [ ] **F3** Proposal review: `events-api`, `events-webapp`. Reviewer assignment is stored by username and binds to the person id on the first call. Queue and score checks match on username or id. Also build scoring, ranking, decide and reopen, plus F1.7 speaker assignment and the F2.4 decision display.
- [ ] **F4** Registration and waitlist: `registration-service`, `events-api`, `events-webapp`. Build the registration service first. Capacity checks and waitlist promotion must be atomic, with promotion in the same request (P4). Then add the events API proxy: a session registration needs a confirmed event registration, and an event cancellation cascades to its sessions. Finally build the web screens, and add the F1 delete-event-with-registrations block.

Product-wide: P1, P2, P3, P4
