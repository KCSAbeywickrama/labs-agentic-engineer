> **Rationale:** Delivers the sign-in, todo/list CRUD, filtering, and completion UI over todo-api, gated on the user-auth Thunder platform resource for OIDC sign-in.

## Scope

Implement the `todo-webapp` React SPA per `specs/design/components/todo-webapp/design.json` and `wireframes.dsl` (screens: SignIn, TodoList, NewTodo, EditTodo, NewList):

- Sign-in: unauthenticated visitor is redirected into Thunder OIDC (Authorization Code + PKCE via oidc-client-ts) before any todo content renders; session persists across visits (automaticSilentRenew, localStorage); expired session triggers silent renew then a redirect if that fails.
- Sign-out ends the session and returns to sign-in.
- Todo list view: todos grouped by list, status filter (all/active/completed), empty-state message when none exist, overdue visual indication.
- Create/edit todo forms: title required (client-side validation on empty), optional description/due date, list assignment; cancel discards edits.
- Complete/reopen toggle with visual distinction.
- Delete todo requires confirmation before deleting.
- List management: create list, delete list (with confirmation and handling of contained todos consistent with the API's move/ask behavior).
- Call `todo-api` for all data operations, attaching `Authorization: Bearer <token>`.

## Acceptance criteria

- Visiting the app unauthenticated shows SignIn first (REQ-001 AC-001-a); after sign-in, shows the user's own todos/lists (AC-001-b); sign-out returns to SignIn (AC-001-c); expired session forces re-auth before any operation (AC-001-d).
- New-todo form rejects empty title with a validation message (REQ-002 AC-002-b) and supports optional description/due date (AC-002-c/d).
- TodoList groups by list, supports status filter, shows empty-state when none exist (REQ-003 AC-003-a/d/e); moving a todo between lists updates immediately (AC-003-c); creating a list with non-empty name works (AC-003-b).
- Edit form persists changes, rejects empty title, cancel discards unsaved changes (REQ-004).
- Complete/reopen toggle updates visual state; overdue incomplete todos are visually flagged (REQ-005).
- Delete requires confirmation (REQ-006 AC-006-b); deleting a non-empty list surfaces the move/ask behavior rather than silently deleting todos (AC-006-c).
